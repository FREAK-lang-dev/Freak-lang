# FREAK 0.16.0

Release date: TBD. A minor release on top of 0.15.2. Programs that built on
0.15.2 still build and behave the same; the headline changes are how
`freak build` produces machine code and what ships in the box.

## Highlights

- **LLVM's IRBuilder is the V3.5 backend.** `freak build` and `freak run`
  now build each LLVM module in process through LLVM 22.1.8's own IRBuilder,
  run the optimizer there and emit an object file directly. Clang is only
  the linker now. Native compile steps are faster (a big image-decoding test
  suite went from 7.5 s to 4.4 s in the native step), and the textual `.ll`
  is still written next to your source.
- **A ready-to-use V4 preview ships in every archive.** Run it with
  `freak v4 build /abs/app.fk --output=/abs/app`. Details below.
- **Call C libraries directly.** `extern [C, link="name"] { ... }` blocks call
  functions in prebuilt `.so`/`.dylib`/`.dll` files, and `load="name"`
  binds them at run time. See `docs/native-ffi.md`.
- **A new build view.** In a terminal, builds show live phase rows with
  millisecond timers and a summary card, and every build-shaped command now
  reports how long it took. Pipes and CI keep the plain output.

## The IRBuilder backend

Nothing to change in your projects. A few knobs if you need them:

- `freak build app.fk --llvm-text` (or `FREAK_IRBUILDER=off` for a whole
  shell) uses the 0.15 path: textual IR handed to clang.
- `--lto=thin|full` builds always link textual IR.
- `FREAK_IRBUILDER_TRACE=1` prints which path a build took.
- `freak doctor` shows `LLVM backend: in-process IRBuilder, LLVM 22.1.8`,
  and `freak doctor --json` has `checks.irbuilder`.

If the IRBuilder ever stumbles on a module, the build prints one dim line
and carries on from the textual IR, so a build that worked on 0.15.2 still
works. Linux and macOS binaries carry LLVM statically and still only need
libc. On Windows, `freak.exe` loads `runtime/LLVM-C.dll` from the install
when it builds; without that file it uses the textual path. Every release
is gated on building the whole test corpus both ways and getting identical
behavior. Background: `docs/v35-irbuilder.md`.

## Native C libraries (FFI)

FREAK can now call functions in prebuilt C shared libraries (`.so`,
`.dylib`, `.dll`) on both backends.

```fk
use std::ffi

extern [C, link="greet"] {
    task greet_add(a: c_int, b: c_int) -> c_int
    @link_name("greet_add")
    task plus(a: c_int, b: c_int) -> c_int
}
```

- `link="name"` links the library at build time (`-lname`). The source
  file's folder is always searched, and `--lib-dir=DIR` / `--link=NAME` add
  more. On Linux and macOS the binary gets an rpath for its own folder.
- `load="name"` skips linking and resolves each task on first call
  (`dlopen` / `LoadLibrary`, next to the executable first). A missing
  library or symbol stops the program with a message that names it.
- Signatures use the `std::ffi` C aliases (`c_int`, `c_long`, `usize`,
  `c_double`, `c_bool`, `*const c_char`, ...) at their real C width, and
  `std::ffi` has helpers for C strings and raw memory. Types that are not
  FFI-safe (`word`, `List`, plain `int`) are rejected by name.
- `extern [C, if target_os = "windows"] { ... }` blocks only apply on that
  target. `@link_name("sym")` binds a FREAK name to a different C symbol.
- The run cache fingerprints every library a build can link, so `freak run`
  rebuilds when a linked library changes.

Full guide: `docs/native-ffi.md`. Bible: §16.2 and §16.7.

## Fixes

- **Hangar works in project folders that other accounts can also write.**
  On Windows, projects on a second drive (like `D:\Projects\app`) inherit
  "Authenticated Users: Modify" and `freak build` / `hangar add` refused
  them with `package transaction original lock parking failed`. The same
  rule broke `hangar init` under `umask 002` on Linux and macOS. Hangar now
  only requires that you own the project folder; its private state under
  `.freak` keeps the strict rules.
- **`==` on lists compares contents.** `["x"] == ["x"]` is `true` now.
- **Passing a `word` to a task no longer copies it.** LLVM builds share the
  string and C builds borrow it, which removes a large hidden cost in
  string-heavy code.
- **New list and string helpers.** `word.split(sep)`, `list.join(sep)` and
  `list.contains(x)`.

## Standard library

- **std::json** escapes strings when it stringifies, so the output is always
  valid JSON, and numbers stringify exactly. Parse errors are now state
  (`json_ok`, `json_last_error`, `json_error_pos`) instead of printed text.
  The parser is iterative and has no container cap, so large documents no
  longer crash, and its pool is only allocated when a program uses JSON. New
  builders and `json_stringify_pretty`.
- **std::algorithm** sorts arrays with a stable O(n log n) merge sort (about
  400x faster at 20k items) and adds `list_sort_int` / `list_sort_word`.
- **std::string** adds UTF-8 aware `reverse`, `trim_left` / `trim_right`,
  `last_index_of`, `index_of_from`, `strip_prefix` / `strip_suffix`,
  `center` and `char_count`.
- **std::convert** adds `base_to_int` and `hex_to_int` / `bin_to_int` /
  `oct_to_int`, and is exact for the smallest `int`.
- **std::version** orders SemVer pre-releases by the spec
  (`alpha.2 < alpha.10 < beta`). Hangar constraint resolution follows it.
- **std::http** decodes chunked bodies and adds `http_resp_header`,
  `http_patch`, `http_request` and a response size cap.

## Bundled V4 preview

Every 0.16.0 release archive now carries a prebuilt **V4 preview compiler**
under `freak/v4/`, and the installers place it at `<install root>/v4/`. You
reach it through the stable CLI:

```bash
freak v4 --version                                   # provenance: source input hash, builder hash, host target
freak v4 check  /abs/path/app.fk                      # V4 frontend + codegen, no output
freak v4 emit   /abs/path/app.fk --output=/abs/path/app.ll
freak v4 build  /abs/path/app.fk --output=/abs/path/app   # app.exe on Windows
```

`freak v4` forwards every argument to `<install root>/v4/freak-v4` and returns
its exit status unchanged. The bundle is built during the release job by
`freak bootstrap-v4` (unlocked mode) from this release's own
`src/compiler/v4`, using the archive's own `freak` binary as the builder, and
each target smoke-builds and runs a shapes + `List` + `for each` program
before the archive is sealed. The locked bootstrap lane stays pinned to its
frozen commit; `--version` therefore prints that declared commit next to
`unlocked-development` — the *source input SHA256* is what identifies the
bytes that were actually compiled.

What is in the box:

| Path | Purpose |
|---|---|
| `v4/freak-v4` | Launcher. Re-hashes the engine and every runtime file on each run. |
| `v4/freak-v4-engine` | The V4 compiler itself (host target, `task main`, panic = abort). |
| `v4/runtime/` | Private, hash-pinned runtime snapshot linked into V4 programs. |
| `v4/bootstrap-report.json` | Build provenance (source, builder, engine and launcher hashes). |

Preview rules of engagement:

- **Outputs are absolute.** `--output` must be an absolute file path (it may
  not point inside `v4/` or at the source), and the source must end in `.fk`.
- **Output folders must be yours.** The checked runtime only publishes into a
  directory owned by you and not writable by other users (POSIX: no group or
  world write bit, so `/tmp` itself is refused — use a folder inside it or in
  your project). On Windows the folder must be owned by your user account
  with no write access for other accounts; folders under your user profile
  qualify, folders created from an elevated (Administrator) shell or directly
  under `C:\` usually do not.
- **Clang 15+ is required** at build time (`FREAK_CLANG` selects one; Windows
  needs the LLVM-MinGW toolchain the installer already recommends).
- Host target only; no cross-compilation yet. V3 (`freak build`) remains the
  default, supported compiler.

No bundle? `freak v4` says so and tells you how to build one yourself from a
source checkout (absolute paths; the output directory must not exist yet).
A self-built preview can also be run directly:

```bash
freak bootstrap-v4 --source=/path/to/src/compiler/v4 --output=/path/to/new-preview
/path/to/new-preview/freak-v4 build program.fk --output=/path/to/program
```

Package-manager note: Scoop and WinGet extract the full archive, so they get
`v4/` too. The Homebrew formula still installs only `bin/`, `runtime/` and
`std/`; Homebrew users can run `freak bootstrap-v4` until the formula learns
about `v4/`.
