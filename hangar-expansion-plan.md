# Hangar Expansion Plan
*FREAK's package manager — from GitHub-releases MVP to a real registry*

---

## Overview

Hangar v1 is intentionally minimal: `hangar.toml` manifests, GitHub Releases as the package source, a flat `hangar_modules/` cache. It works. It's shippable.

But a real ecosystem needs a real registry. This document scopes out the full Hangar v2 expansion: a centralized index, a publishing workflow, a search API, dependency resolution, security infrastructure, and CLI improvements — in priority order.

The design philosophy stays the same: fast, opinionated, weeb-coded.

## HG1 — SemVer + Lockfile

**The single most important change before anything else.**

### SemVer constraints in `hangar.toml`

```toml
[dependencies]
muvluv      = "^1.2.0"          # compatible with 1.x.x, ≥1.2.0
freak-ui    = "~2.4.0"          # patch-compatible, ≥2.4.0 <2.5.0
freak-math  = "=0.9.1"          # exact pin
freak-http  = ">=1.0.0 <2.0.0"  # range
```

Support the full SemVer constraint syntax: `^`, `~`, `=`, `>=`, `<`, `>`, `<=`, and bare versions (treated as `^`).

### `hangar.lock`

A deterministic lockfile generated on first install, committed to version control.

```toml
# This file is auto-generated by Hangar. Do not edit manually.
# Generated: 2025-10-14T11:30:00Z

[[package]]
name    = "muvluv"
version = "1.3.1"
source  = "registry+https://index.hangar.dev"
sha256  = "a3f1b2c9..."

[[package]]
name    = "freak-ui"
version = "2.4.7"
source  = "registry+https://index.hangar.dev"
sha256  = "d8e9f0a1..."
```

`hangar install` with an existing lockfile is fully reproducible — resolves nothing, just fetches the exact pinned versions. `hangar update` runs resolution fresh.

### CLI changes

```
hangar install           # installs from lockfile if present; resolves + writes lockfile if not
hangar update            # re-resolves all constraints, writes new lockfile
hangar update muvluv     # re-resolves only one package
hangar outdated          # shows packages with newer matching versions available
```

## HG2 — Central Registry Index

The registry index is the heart of Hangar v2. It's what makes `hangar install muvluv` work without a git URL.

### Architecture

The index is a **static Git repository** (like crates.io's sparse index) served over HTTPS. No database required for reads. Writes go through the registry API.

```
index.hangar.dev/
  mu/
    mv/
      muvluv          ← newline-delimited JSON, one line per version
  fr/
    ea/
      freak-ui
      freak-http
      freak-json
```

Each index file is a series of JSON lines, one per published version:

```json
{"name":"muvluv","vers":"1.0.0","deps":[...],"sha256":"abc...","yanked":false}
{"name":"muvluv","vers":"1.1.0","deps":[...],"sha256":"def...","yanked":false}
{"name":"muvluv","vers":"1.2.0","deps":[...],"sha256":"ghi...","yanked":false}
```

### Why static?

- No server needed for read path — just GitHub Pages or Cloudflare Pages
- Clients can clone or fetch partial index diffs
- Transparent: anyone can audit every version ever published
- CDN-friendly by default

### Registry API (write path only)

A small API server handles publishing and yanking. Read operations don't touch it.

```
POST /api/v1/publish         # publish a new version
DELETE /api/v1/yank          # yank a version
PUT /api/v1/unyank           # un-yank a version
GET  /api/v1/me              # validate auth token
```

### Package storage

Tarballs go to a content-addressed store:

```
packages.hangar.dev/
  muvluv/
    1.0.0/
      muvluv-1.0.0.tar.gz
      muvluv-1.0.0.sha256
    1.1.0/
      ...
```

For v2, this can just be a GitHub Releases mirror with the index on top. No custom infra needed until traffic demands it.

### `hangar.toml` update

Add an optional `[registries]` section for overrides:

```toml
[registries]
default = "https://index.hangar.dev"

# Optional: add a custom registry alongside the default
corp = "https://hangar.internal.mycompany.com"
```

Packages can reference a specific registry:

```toml
[dependencies]
muvluv        = "^1.0"
internal-auth = { version = "^2.0", registry = "corp" }
```

## HG3 — `hangar publish`

The publishing flow. Simple, opinionated, no nonsense.

### What gets published

A package tarball containing:

```
muvluv-1.2.0/
  hangar.toml       ← manifest (required)
  src/              ← source files (required)
  README.md         ← shown on hangar.dev
  LICENSE           ← shown on hangar.dev
  CHANGELOG.md      ← optional but encouraged
```

Everything else (build artifacts, hangar_modules/, tests) is excluded by default. Add explicit `include` or `exclude` lists to `hangar.toml`:

```toml
[package]
name        = "muvluv"
version     = "1.2.0"
authors     = ["teri <teri@freak-lang.dev>"]
description = "The flagship FREAK anime standard library"
license     = "MIT"
repository  = "https://github.com/freak-lang/muvluv"
keywords    = ["anime", "stdlib", "muvluv"]
categories  = ["standard-libraries", "multimedia"]

exclude = [
  "tests/fixtures/large-*",
  "*.tmp"
]
```

### Publish flow

```bash
# One-time: authenticate
hangar login

# Dry run — shows what would be uploaded
hangar publish --dry-run

# Publish
hangar publish
```

Hangar verifies before upload:
- Version not already published (versions are immutable)
- `hangar.toml` is valid
- All declared dependencies exist in the registry
- Tarball sha256 matches what gets stored

### Auth

Token-based. Tokens are scoped per-package or per-namespace.

```bash
hangar login                   # opens browser, stores token in ~/.hangar/credentials
hangar token create --scope muvluv
hangar token revoke <token-id>
```

For CI, set `HANGAR_TOKEN` env var. Hangar picks it up automatically.

### Yanking

Yanking marks a version as broken without deleting it. Existing lockfiles referencing it still work. New dependency resolution avoids it.

```bash
hangar yank muvluv@1.1.0 --reason "critical memory safety bug"
hangar unyank muvluv@1.1.0
```

Yanked versions show a warning on hangar.dev and in `hangar install` output.

## HG4 — Search (CLI + Web)

### CLI search

```bash
hangar search anime
hangar search anime --limit 10
hangar search "freak ui"
```

Output:

```
muvluv            1.3.1   The flagship FREAK anime standard library
freak-ui          2.4.7   Immediate-mode UI framework for FREAK
freak-vn          0.8.0   Visual novel runtime utilities
anime-math        1.0.2   Power-level arithmetic and stat systems
```

Flags:
- `--sort downloads|recent|alpha` (default: relevance)
- `--category <cat>`
- `--json` — machine-readable output

### Search index

The index supports full-text search over: name, description, keywords, categories, author. The static index doesn't support this natively — use a pre-built search index file served from the CDN, updated on each publish.

Format: a single `search-index.json` (or gzipped variant) with all package metadata. Clients download it once and cache it locally for offline/fast search. Refreshes on TTL or explicit `hangar search --refresh`.

### hangar.dev search

The web UI (HG7) exposes search at `hangar.dev/search?q=...` with the same results, plus filtering by category, download counts, and last-updated date.

## HG5 — Checksum + Signature Verification

Never trust a download.

### SHA-256 verification

Every tarball has a companion `.sha256` file. Hangar verifies the hash before extracting. If it doesn't match: hard stop, no install.

This is already partially scoped in the lockfile design (HG1) — the lock stores sha256 per package.

### Signing (v2.1+)

For the initial registry launch, sha256 is enough. Later, add optional publisher signing using ed25519 keys:

```
hangar keyring add muvluv <pubkey>
hangar keyring trust freak-lang-dev
```

Signed packages show a ✓ in the registry UI and CLI output. Unsigned packages show a neutral indicator — not an error. Signed-and-tampered packages are a hard error.

### `hangar audit`

A security-focused subcommand:

```bash
hangar audit              # check all deps for known advisories
hangar audit --fix        # auto-update to patched versions where SemVer allows
```

Advisory database: a simple JSON file maintained in the `hangar-advisories` GitHub repo and bundled into the index. Format mirrors the RustSec advisory DB.

## HG6 — Dependency Resolution Engine

The current implementation installs dependencies one-by-one with no conflict detection. HG6 replaces this with a real resolver.

### Algorithm

Use a variant of PubGrub (the algorithm behind Dart's pub and Cargo's modern resolver). It's:
- Correct (finds a solution if one exists, proves impossibility otherwise)
- Fast in practice (backtracks minimally)
- Error messages are actually good

The resolver works on a constraint graph:
- Root package declares version constraints
- Each candidate package version declares its own constraints
- Resolver finds a set of concrete versions satisfying all constraints simultaneously

### Error messages

Resolution failures get the FREAK treatment. Instead of:

```
error: no version of muvluv satisfies both ^1.0 and ^2.0
```

You get:

```
[YUUKO] Resolution failed. Two dependencies want incompatible versions of muvluv:
        freak-vn 0.8.0  requires  muvluv ^2.0.0
        your project    requires  muvluv ^1.3.0
        These ranges do not overlap.
        Suggestion: update your muvluv constraint to ^2.0 or pin freak-vn to an older version.
```

(Voice character selection applies here per M7 / Opus voice system.)

### Features / optional dependencies

```toml
[dependencies]
muvluv = { version = "^1.0", features = ["tda", "unlimited"] }
```

Feature flags gate optional code paths within a package. The resolver factors features into constraint solving. A package can have `default-features = false`.

## HG7 — Registry Web UI (hangar.dev)

The public face of the Hangar ecosystem.

### Pages

**`/`** — landing page
- Search bar (prominent)
- Stats: total packages, total downloads, newest packages
- Featured / curated packages section

**`/package/muvluv`** — package page
- Name, description, latest version, all versions
- README rendered as HTML
- `hangar.toml` snippet to copy
- Dependency tree visualization
- Download count (all time + last 30 days)
- Links: repository, documentation, license
- Owners + publish history
- Yank notices

**`/search?q=anime`** — search results
- Full-text search
- Filter by category, sort by relevance/downloads/recent
- Pagination

**`/user/teri`** — user/org page
- Published packages, total downloads

**`/categories`** — category index

### Tech stack

Static site generation (at publish time) for package pages + SSR/edge functions for search. No heavyweight backend. Cloudflare Pages is the target deployment.

Aesthetic: on-brand with FREAK docs. Dark theme, monospace accents, minimal but distinctive. Not a Crates.io clone.

## HG8 — Namespaces / Orgs

Scoped packages under a namespace prefix:

```toml
[dependencies]
"@freak-lang/muvluv" = "^1.0"
"@freak-lang/freak-ui" = "^2.0"
```

Namespaces are claimed by verified orgs. The `@freak-lang` namespace is reserved for official packages.

Unscoped names continue to work as before. Namespaces are opt-in, not required.

## HG9 — Private Registries

Teams can run their own Hangar registry for internal packages:

```toml
[registries]
default = "https://index.hangar.dev"
acme    = "https://hangar.acme.internal/index"

[dependencies]
muvluv      = "^1.0"                              # from default
acme-auth   = { version = "^3.0", registry = "acme" }
```

Private registries use the same static-index protocol as the public one. The registry server is a small open-source binary (`hangar-registry`) that teams can self-host.

Auth for private registries: same token system, configured per-registry in `~/.hangar/credentials`.

---

## HG10 — Mirrors + CDN

For reliability and speed:

- The official index is mirrored on at least two CDN providers
- Clients can configure a preferred mirror: `[net] mirror = "https://hangar-mirror.example.com"`
- Package tarballs are served from a CDN with edge caching
- The `sha256` lockfile entries make mirror trust a non-issue — tampered tarballs get caught at the client

## CLI Reference (full v2 surface)

```
hangar init [name]           Create a new FREAK project
hangar install               Install from lockfile (or resolve + write lockfile)
hangar update [package]      Re-resolve and update lockfile
hangar add <package> [ver]   Add a dependency and install it
hangar remove <package>      Remove a dependency
hangar outdated              List packages with newer versions available

hangar publish               Publish current package to the registry
hangar publish --dry-run     Show what would be uploaded, don't upload
hangar yank <pkg>@<ver>      Yank a published version
hangar unyank <pkg>@<ver>    Un-yank a version

hangar search <query>        Search the registry
hangar info <package>        Show package details
hangar tree                  Print dependency tree

hangar login                 Authenticate with the registry
hangar logout                Remove stored credentials
hangar token create          Create a new API token
hangar token revoke <id>     Revoke an API token

hangar audit                 Check dependencies for known advisories
hangar audit --fix           Auto-update to patched versions

hangar clean                 Remove cached packages from hangar_modules/
hangar verify                Re-verify all installed packages against lockfile hashes
```

## Open Questions

1. **Domain** — hangar.dev is the obvious choice. Is it available? Alternatives: hangar.fk, gethangar.dev, freakpkg.dev.
2. **Index hosting** — GitHub Pages (free, simple) vs Cloudflare Pages (edge performance). Both work for Phase 2.
3. **Advisory DB** — Maintain ourselves or federate with existing DB? Low volume initially, could be a simple YAML file in the main repo.
4. **Feature flags** — Full feature flag system (Cargo-style) or a simpler capability system? Adds significant resolver complexity.
5. **Download counts** — Requires server-side tracking. Phase 2 can skip this and add it in Phase 3.
